Which Bluetooth. Everything on this page is Bluetooth Low Energy (BLE), Bluetooth 4.0 and later — not Classic Bluetooth (BR/EDR), the one headphones stream audio over. The two share a name and the 2.4 GHz band, and nothing else on air; a BLE-only device cannot talk to a Classic-only one.

BLE — this repositoryClassic BR/EDR — not covered
channels40 × 2 MHz: 3 for advertising (37, 38, 39), 37 for data79 × 1 MHz
hoppingonce per connection event; the phone–laptop link here: every 30 ms, about 33 hops/severy 625 µs slot, up to 1600 hops/s
made forshort exchanges, sleeping in betweencontinuous streams
pairingLE Secure Connections: ECDH, f4, g2 — belowSecure Simple Pairing

Neither hop sequence is secret: both follow from parameters sent in the clear. Hopping avoids accidental interference; it does not stop a jammer, and BLE's three advertising channels are easy to jam together.

03.2

RSSI is not distance, even when nobody lies

lecture 2–4

Two smart bulbs that never moved, heard for 40 minutes. A single packet's RSSI spans 8 dB between its 5th and 95th percentile — under free-space path loss, a factor of 2.5 in distance. That is the honest case; an attacker simply transmits louder.

03.3

Pair once, then 80 ms

timeline.py · report 02

The same phone and laptop, a week apart. The first pairing attempt died of the 30-second SMP timeout — to the user, an ordinary disconnection. The second was confirmed and the link encrypted at 38 s, most of it waiting for a person. A week later the bonded phone reconnected and the link was encrypted 80 ms after it came up, with no pairing at all: the controller asked its host for the stored Long Term Key and got it. That key crosses HCI in clear — the timeline prints that it was given, never what.

03 + 01 + 02 · one read, layer by layer

One packet, every layer

the phone reads Battery Level · frame 371

Each layer wraps the one inside it: its header in front, the inner layer's whole PDU as its payload. The ATT request 0a 24 00 — “read attribute 0x0024” — travels inside an L2CAP PDU, which travels inside a Link Layer packet on air. The HCI ACL header is never on air: it exists only on the wire between the host and the Bluetooth chip, where the controller swaps it for the LL header. Everything in a box is part of some layer's PDU; only the preamble, access address and CRC frame the packet around the PDUs.

Bottom row: the capture, byte for byte. Top row: from the Core spec (Vol 6 Part B 2.1, 2.4) — the host never sees the preamble, access address, LL header or CRC, so their values are in no capture here. The connection was not yet encrypted: no MIC. On air the PDU and CRC are also whitened, XORed with a sequence that depends on the channel.

The ACL header, bit by bit. Four bytes hold four values, because handle, PB and BC share one 16-bit word; ble_acl_t has a fifth field, data, which is not in the header at all but points just past it. The word is little-endian, so the second byte on the wire is its high byte. On air none of this exists: the LL header carries the same boundary flag as LLID and the same length, and no handle.

Every field, named. The same packet, one part at a time, in the order the bytes travel. Values are from frame 371; ? marks a field the controller fills in on air, which no HCI capture can show. Bit strips are drawn most significant bit first; bytes on the wire are little-endian. Over UART the ACL packet is also preceded by an H4 indicator byte 0x02; over USB, as here, it is not.

LL header

2 bytes · on air only · controller · first byte drawn bit 7 → bit 0

RFU0CP0MD?SN?NESN?LLID10Length0x07
LLID2 bit10Link Layer ID. 10: start of an L2CAP message, or a whole one. 01: continuation, or an empty packet. 11: a link-layer control PDU (LL_*), which never reaches the host.
NESN1 bit?Next Expected Sequence Number: acknowledges the other side's last packet (flips) or asks for it again (does not).
SN1 bit?Sequence Number of this packet, 0 or 1, so a retransmission is recognised as a repeat.
MD1 bit?More Data: the sender has more to send in this connection event, so the event stays open.
CP1 bit0CTEInfo Present: a 1-byte CTEInfo field follows the header (direction finding). 0 here.
RFU2 bit00Reserved for future use.

ATT PDU

3 bytes here · on air and over HCI · host stack · opcode drawn bit 7 → bit 0

Sig0Cmd0Method001010Attribute Handle24 00 → 0x0024
Sig flag1 bit0Authentication Signature flag, opcode bit 7: a 12-byte signature ends the PDU (signed write only).
Cmd flag1 bit0Command flag, opcode bit 6: a command, which gets no response (Write Command).
Method6 bit0x0AOpcode bits 5–0: what to do. 0x0A Read Request. Opcode = flags + method = 0x0A.
Attribute Handle16 bit0x0024Which attribute, little-endian. Project 02's GATT table puts Battery Level at 0x0024. Other opcodes carry other parameters here.

All tests passed; the first phone could read nothing

android · nrf connect

Every read came back ATT 0x0E Unlikely Error. A helper method named _name was silently replaced: dbus.service.Object.__init__ sets self._name to the bus name, None. 02.2

The device chose 0xFF; the phone got 0x80

bluez source

A 50 ms sample interval is out of range, and the Core Specification Supplement names 0xFF for exactly that. BlueZ 5.72's dbus_error_to_att_ecode() maps org.bluez.Error.Failed to 0x80 and accepts only 0x80–0x9F: a D-Bus application cannot send 0xE0–0xFF at all.

The six digits on both screens

numeric comparison, LE Secure Connections

985572

on the phone · in bluetoothctl · and computed by project 01's ble_sc_g2 from the capture

Writing the Identify characteristic before pairing came back 0x05 Insufficient Authentication, and the phone started pairing on its own. Both sides declared KeyboardDisplay, so numeric comparison: each side computes g2(PKax, PKbx, Na, Nb) and shows the last six digits; a man in the middle holds a different key pair with each side, and the numbers differ. 04 · lecture 10, on air

Advertising privacy audit

rotation is supposed to make a device untraceable — does it?
04.1

The address rotated; the payload did not

python · stdlib

A device sending Google service data changed its address every few minutes, but its 20-plus-byte payload only every 10–20. Four of its six address changes carried the payload over byte for byte, 0.1–3.1 s apart — those links are certain. At the other two, address and payload changed together; those are linked only by timing and signal strength, and marked as probable. With them, seven addresses make one 40-minute trace.

04.2

Three ways to track a light bulb

spec violation

A public address that never changes; a name ending in two bytes of that address; and LE Limited Discoverable held for 40 minutes where the spec allows 180 seconds — from a company ID not in the Bluetooth SIG's assigned numbers.

P001  warning  public#97c4e4   public address, heard for 40.0 of 40.0 min: trackable wherever it goes, it never changes
P003  warning  public#97c4e4   advertised name (18 chars) contains the last two bytes of the device's own address
S001  warning  public#97c4e4   advertised LE Limited Discoverable for 40.0 min; the spec caps it at 180 s (TGAP(lim_adv_timeout))
04.3

A false positive, found on real data

regression test

The first version linked three Apple devices because they shared a 17-byte payload. It was 01 00 00 … 80 00 00 00 00 — a bitmap every device in the same state sends, not a fingerprint. A payload now counts as an identifier only with 6+ bytes and 4+ distinct values; the test fails without the rule.

Not done yet, and said so in the READMEs:

  • 01 on a real Cortex-M board — sizes and stack come from the cross-compiler.
  • Reconnecting on the stored LTK; the 0.5 s notification limit on air; Privacy = device for the laptop's own address.
  • f4 in C — it is computed above in Python, to check the capture.

The cryptography here is for understanding: a product should use the chip's hardware AES and a qualified stack. Captures stay out of the repository — they hold other people's addresses, and the pairing's keys. Built alongside Foundations of Wireless Security, Saarland University, summer 2026.
